1. PROJECT OVERVIEW
--------------------------------------------------------------------------------
Trainly is a modern, full-stack Learning Management System (LMS) designed for 
both Students and Educators. It features a dual-portal interface, seamless payment 
gateway integration, real-time video lecture progress tracking, content-based course 
recommendation engine, role-based access control (RBAC), media hosting CDN, webhook 
event streaming, and an embedded AI chatbot assistant.

Key Portals:
  - Student Portal: Course browsing, search/filter, detailed preview, video lecture
    player with progress tracking, Stripe checkout, ratings & reviews, smart 
    course recommendations, and AI Assistant.
  - Educator Portal: Upgrade role to instructor, rich-text course creation editor
    (Quill JS), multi-chapter & multi-lecture dynamic builder, Cloudinary image upload, 
    analytics dashboard (total revenue, enrollment count, earnings breakdown).


2. DETAILED TECHNOLOGY STACK
--------------------------------------------------------------------------------
FRONTEND (Client-side):
  - Core Framework: React 19 (ES6 Module architecture)
  - Build Tool & Dev Server: Vite (Lightning fast HMR & bundling)
  - Routing: React Router DOM v7 (Declarative client routing, nested layouts)
  - Styling & UI: Tailwind CSS v3, Lucide React (modern icons)
  - Rich Text Editing: Quill JS (for HTML course descriptions)
  - Progress Visualization: rc-progress (lecture completion progress bars)
  - State Management: React Context API (AppContext for global state management)
  - Authentication SDK: @clerk/clerk-react (Session management, OAuth, JWT handling)
  - HTTP Client: Axios (with Bearer JWT authorization headers) + Fetch API fallback
  - Video Streaming Component: react-youtube (YouTube API integration)
  - Time & Duration Utility: humanize-duration (formats seconds/minutes into human readable strings)
  - Notifications: react-toastify (Toast notifications)

BACKEND (Server-side):
  - Environment: Node.js (v18+)
  - Framework: Express.js (v5 - latest Express with native async error handling)
  - Database: MongoDB Atlas (NoSQL Cloud Database)
  - Database ODM: Mongoose v9 (Schema modeling, population, references)
  - Authentication Middleware: @clerk/express (clerkMiddleware, getAuth, clerkClient)
  - Webhooks Handling:
      * Svix SDK (Verifies Clerk webhook signature headers: svix-id, svix-timestamp, svix-signature)
      * Stripe SDK (Verifies raw body signature for payment events)
  - Payment Processor: Stripe Node.js SDK (Stripe Checkout Sessions & PaymentIntents)
  - Cloud Storage CDN: Cloudinary v2 SDK (For thumbnail hosting & asset delivery)
  - File Upload Handler: Multer (Multipart form data middleware)
  - Server Management: Nodemon (Hot reload), dotenv (Environment variables), cors (CORS handling)


3. DATABASE ARCHITECTURE & MONGOOSE MODELS
--------------------------------------------------------------------------------
1. User Model ('User'):
   - _id: String (Primary Key - syncs directly with Clerk User ID e.g., 'user_xxx')
   - name: String
   - email: String
   - imageUrl: String
   - enrolledCourses: Array of ObjectIds (ref: 'Course')
   - timestamps: createdAt, updatedAt

2. Course Model ('Course'):
   - courseTitle: String

   - courseThumbnail: String (Cloudinary CDN URL)
   - coursePrice: Number/String
   - discount: Number (Percentage 0-100)
   - isPublished: Boolean (Draft vs Published state)
   - courseContent: Array of Chapter schemas:
       * chapterId: String
       * chapterOrder: Number
       * chapterTitle: String
       * chapterContent: Array of Lecture schemas:
           - lectureId: String
           - lectureTitle: String
           - lectureDuration: Number (Minutes)
           - lectureurl: String (Video URL)
           - isPreviewFree: Boolean (Public preview toggle)
           - lectureOrder: Number

   - educator: String (ref: 'User' Clerk ID)

3. Purchase Model ('Purchase'):
   - courseId: ObjectId (ref: 'Course')
   - userId: String (ref: 'User')
   - amount: Number (Final calculated price)

4. CourseProgress Model ('CourseProgress'):
   - userId: String
   - courseId: String
   - completed: Boolean
   - lectureCompleted: Array of Strings (Array of completed lecture IDs)


4. SYSTEM ARCHITECTURE & INTEGRATION FLOWS
--------------------------------------------------------------------------------
A. AUTHENTICATION & USER SYNCHRONIZATION FLOW:
   1. User signs in on frontend via Clerk React SDK components.
   2. Clerk issues a secure JWT token.
   3. Webhook Sync: Clerk emits a 'user.created' or 'user.updated' event to backend '/clerk'.
   4. The backend uses Svix to verify headers (svix-id, svix-timestamp, svix-signature) and updates MongoDB User collection.
   5. Fallback Sync: Every protected endpoint has a helper `syncUserFromClerk(userId)` to ensure DB consistency even if webhooks are delayed.

B. PAYMENT & ENROLLMENT LIFECYCLE (STRIPE & WEBHOOKS):
   1. Student clicks 'Enroll Now' -> Frontend calls `POST /api/user/purchase` with Bearer token.
   2. Backend calculates discounted price: `price - (discount * price / 100)`.
   3. Backend creates a `Purchase` document with status = 'pending'.
   4. Backend creates a Stripe Checkout Session, passing `purchaseId` in metadata.
   5. Backend returns `session.url`, redirecting student to Stripe payment page.
   6. Upon successful payment, Stripe fires `payment_intent.succeeded` webhook to `/stripe`.
   7. Backend verifies `stripe-signature` using raw JSON body.
   8. Backend extracts `purchaseId` from session metadata, updates `Purchase.status = 'completed'`, adds student to `Course.enrolledStudents`, and adds course to `User.enrolledCourses`.

C. CONTENT-BASED COURSE RECOMMENDATION ALGORITHM:
   - Located in `userController.js` -> `calculateCourseScore`
   - Weighted scoring algorithm:
       1. Keyword Match (35% weight): Tokenizes title & description (filtering stop words), comparing with student's enrolled courses.
       2. Rating Match (20% weight): Compares course rating with average rating of student's past enrolled courses.
       3. Price Match (15% weight): Evaluates price difference against student's average spending pattern.
       4. Popularity/Enrollments (15% weight): Normalized score based on total enrolled students.
       5. Published Status (15% weight): Boosts published active courses.
   - Result: Generates personalized top 6 recommended courses for each student homepage!

D. CONTENT PROTECTION & PREVIEW SECURITY:
   - When an unauthenticated or unenrolled user requests course details (`GET /api/course/:id`), the server iterates through chapters and lectures.
   - If `lecture.isPreviewFree === false`, the server strips `lectureurl = ""` before sending response. This guarantees video URL privacy on the server side!

E. EDUCATOR COURSE CREATION & CLOUDINARY CDN INTEGRATION:
   - Educator fills course metadata, chapters, and attaches thumbnail image.
   - Payload sent as `multipart/form-data`.
   - Multer middleware intercepts file on server.
   - Cloudinary SDK uploads thumbnail image to cloud CDN and returns `secure_url`.
   - Mongoose stores structured course schema into MongoDB.


5. API ROUTE REFERENCE MAP
--------------------------------------------------------------------------------
PUBLIC / COURSE ROUTES (`/api/course`):
  - GET  `/all`                 -> Fetch all published courses (public overview)
  - GET  `/:id`                 -> Fetch single course details (with URL privacy filter)

STUDENT / USER ROUTES (`/api/user`):
  - GET  `/data`                -> Fetch current logged-in user profile & role
  - GET  `/enrolled-courses`    -> Fetch all courses student has purchased
  - POST `/purchase`            -> Create Stripe checkout session
  - POST `/update-course-progress` -> Mark lecture as complete
  - POST `/get-course-progress` -> Fetch completed lectures array for player
  - POST `/add-rating`          -> Rate/Review an enrolled course (1-5 stars)
  - GET  `/recommendations`     -> Fetch top AI recommendation courses

EDUCATOR ROUTES (`/api/educator`):
  - GET  `/update-role`         -> Update Clerk user metadata role to 'educator'
  - POST `/add-course`          -> Create course + upload thumbnail to Cloudinary
  - GET  `/courses`             -> Fetch all courses published by educator
  - GET  `/dashboard`           -> Fetch analytics (total earnings, student counts)
  - GET  `/enrolled-students`   -> Fetch list of enrolled students & transaction history

WEBHOOK ENDPOINTS:
  - POST `/clerk`               -> Svix verified Clerk user lifecycle webhook
  - POST `/stripe`              -> Raw body verified Stripe payment webhook


6. TOP INTERVIEW QUESTIONS & IMPACTFUL ANSWERS
--------------------------------------------------------------------------------
Q1: "Explain the architecture of your LMS application."
A: "It's a full-stack MERN application built with React 19, Vite, Express v5, and MongoDB Atlas. I designed it with a dual portal for Students and Educators. Authentication is managed via Clerk JWTs and synchronized asynchronously via Svix webhooks. Payments use Stripe Checkout with raw body webhook listeners for atomic enrollment processing. Media is hosted on Cloudinary."

Q2: "How did you secure paid course content?"
A: "Content protection happens at the server level. In `courseController.js`, when a non-enrolled user requests course data, the backend iterates over all chapters and lectures. If a lecture's `isPreviewFree` flag is false, the `lectureurl` property is stripped out to empty string before responding, preventing network inspection leaks."

Q3: "How does the course recommendation system work?"
A: "I implemented a content-based recommendation engine in `userController.js`. It calculates a dynamic matching score based on 5 weighted criteria: title/description keyword overlap (35%), rating preferences (20%), price similarity to past purchases (15%), course popularity (15%), and publication status (15%)."

Q4: "How do webhooks ensure data consistency between Clerk, Stripe, and MongoDB?"
A: "Webhooks allow asynchronous decoupling. For Clerk user management, we verify signatures using the Svix library (`svix-id`, `svix-timestamp`, `svix-signature`). For Stripe payment fulfillment, we handle raw JSON payloads (`express.raw()`) to verify `stripe-signature`. Upon payment success, Stripe triggers an event carrying the purchase ID metadata, which atomically marks the purchase complete and updates Mongoose arrays in both Course and User models. I also built fallback sync logic in `syncUserFromClerk()` to guarantee reliability if a webhook is missed."

Q5: "How is global state handled in the frontend?"
A: "We use React Context API (`AppContext.jsx`) to centralize user authentication state, enrolled courses, course lists, recommendation data, and duration calculation helper utilities (`humanize-duration`). Frontend components consume state cleanly via `useContext(AppContext)`."
